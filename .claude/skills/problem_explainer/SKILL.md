# Skill: problem_explainer

该 skill 用于为算法题生成可视化解释页面，帮助理解算法执行过程，而不仅仅是输出文字题解。

其核心目标是：

- 为每一道算法题生成一个静态 HTML 解释页面
- 通过图形化方式展示输入、状态变化和执行步骤
- 结合“计步器 / 步骤控制器”逐步查看算法执行过程
- 让用户可以直观看到每一步发生了什么
- 所有解释文件统一放置在题目目录下的 explain 文件夹中

---

## 使用目标

当某道题需要更直观的讲解时，该 skill 应生成一个可离线查看的静态 HTML 页面，用于展示：

- 题目背景或目标
- 输入示例
- 算法执行的分步骤演示
- 每一步的状态变化
- 图像化或结构化展示
- 最终结果与过程总结

该页面应该适合“看过程理解算法”，而不是只看结论。

---

## 输出目录规范

所有解释页面都必须放在对应题目的 explain 目录下。

目录结构要求如下：

- lcXXX_problem_name/
    - lcXXX_problem_name.java
    - README.md
    - explain/
        - index.html
        - style.css
        - script.js
        - assets/（可选）

说明：

1. explain 目录必须位于题目目录内部
2. explain/index.html 作为默认入口页面
3. 如无必要，不生成多余文件
4. 所有资源必须为静态资源，不依赖后端服务

---

## 页面目标

生成的 HTML 页面需要满足以下要求：

### 1. 页面为静态 HTML

- 可直接在本地打开
- 不依赖服务端
- 不依赖打包工具
- 不依赖复杂工程配置

优先使用：

- 原生 HTML
- 原生 CSS
- 原生 JavaScript

如确有必要，可少量使用轻量级前端逻辑，但应保持简单。

---

### 2. 必须体现“步骤化”

页面必须能逐步展示算法执行过程，而不是一次性展示最终答案。

应至少具备以下能力：

- 当前步骤编号显示
- 上一步 / 下一步切换
- 当前步骤说明
- 当前状态可视化展示
- 最终结果展示

如果适合，还可以加入：

- 自动播放
- 重置
- 跳转到指定步骤

---

### 3. 必须体现“可视化”

页面要尽可能把抽象算法过程变成可视化内容。

例如：

- 数组题：展示数组变化、指针移动、区间变化
- 链表题：展示节点连接关系、指针指向变化
- 树题：展示树结构、高亮当前访问节点
- 图题：展示节点和边、高亮遍历路径
- 动态规划：展示状态表变化、当前转移位置
- 回溯：展示递归路径、选择与撤销过程
- 滑动窗口：展示窗口左右边界和窗口内部元素
- 单调栈：展示栈内容变化
- 二分查找：展示 left、right、mid 的变化

可视化必须服务于理解，不要为了“炫”而堆效果。

---

## 讲解内容要求

生成的解释页面应尽量包含以下模块：

### 1. 题目概览

包括但不限于：

- 题号
- 题目名称
- 题型
- 核心解法标签

---

### 2. 示例输入输出

应展示至少一组典型示例，包括：

- 输入
- 输出
- 简要解释

示例必须和可视化步骤保持一致。

---

### 3. 解题思路

用简洁、清晰的语言说明：

- 为什么使用当前算法
- 整体思路是什么
- 状态是如何变化的

说明应控制篇幅，避免写成长篇题解文章。

---

### 4. 步骤演示区

这是页面的核心区域，必须包含：

- 当前步骤编号
- 当前步骤文字说明
- 当前状态图示
- 被高亮的关键位置或元素

例如：

- 当前正在比较哪两个元素
- 当前指针位置在哪
- 当前栈内容是什么
- 当前递归路径是什么
- 当前 DP 表更新到了哪里

---

### 5. 复杂度说明

页面中应提供：

- 时间复杂度
- 空间复杂度

说明保持简洁即可。

---

### 6. 关键易错点

页面中应补充当前题的常见坑点，例如：

- 边界条件
- 指针越界
- 重复元素处理
- 递归回溯撤销
- 初始状态设置
- null 判断

---

## 交互要求

生成的页面默认应包含以下交互能力：

- 下一步
- 上一步
- 重置
- 当前步骤显示

建议支持以下增强能力：

- 自动播放
- 播放速度调节
- 步骤列表
- 进度条

但应优先保证清晰和稳定，不要过度复杂化。

---

## 风格要求

页面风格应符合以下原则：

- 简洁
- 清晰
- 可读
- 面向学习
- 不花哨
- 不依赖重动画
- 不做复杂 UI 框架

重点不是做一个“产品页面”，而是做一个“便于理解算法过程的学习页面”。

---

## 文件生成规则

在执行该 skill 时，必须遵循以下规则：

### 1. 只在题目目录下创建 explain 文件夹

禁止把解释页面放到仓库根目录或其他无关位置。

---

### 2. explain 文件夹内默认生成 index.html

如果没有特别说明，统一使用：

- explain/index.html

作为主入口文件。

---

### 3. 尽量拆分静态资源

如果页面逻辑和样式较多，应拆分为：

- index.html
- style.css
- script.js

如果内容很简单，也可以只生成一个 index.html，但应保持结构清晰。

---

### 4. 不修改原有算法代码逻辑

该 skill 的职责是生成解释页面，不负责重写算法实现。

---

### 5. 解释内容必须和当前题目的代码逻辑一致

不能只根据题目泛泛生成示意图，必须尽量贴近当前题目采用的真实解法。

例如：

- 如果代码使用双指针，就展示双指针过程
- 如果代码使用 BFS，就展示 BFS 队列变化
- 如果代码使用 DP，就展示 DP 表更新

- 链表
- 栈与队列
- 单调栈
- 二叉树
- 图论
- 回溯
- 二分查找
- 动态规划
- 设计题

## 生成内容时的优先级

在生成 explain 页面时，请按以下优先级处理：

1. 优先保证步骤清晰
2. 优先保证状态变化可看懂
3. 优先保证和代码逻辑一致
4. 再考虑页面美观
5. 避免无意义炫技效果

- 页面标题区
- 题目信息区
- 示例输入输出区
- 解题思路区
- 步骤控制区
- 可视化展示区
- 当前步骤说明区
- 复杂度与易错点区

## 注意事项

- 页面必须可本地直接打开
- 页面必须适合作为“学习辅助工具”
- 页面重点是“过程展示”，不是“最终答案展示”
- 所有命名和目录应与题目目录保持一致
- 若某题不适合复杂图形，也必须至少提供结构化步骤可视化

---

## 总结

problem_explainer 的核心职责是：

- 为算法题生成静态 HTML 讲解页面
- 用图像化方式展示算法执行过程
- 提供逐步查看能力
- 将生成内容统一存放到题目目录下的 explain 文件夹中

所有输出都应围绕“帮助理解每一步发生了什么”这一目标展开。
